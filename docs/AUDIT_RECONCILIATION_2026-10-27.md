## Design proposal: database-backed paginated shortlist (not implemented)

**Purpose and boundary.** Enable staff to review larger imported cohorts without presenting truncated evidence as a complete qualification. Existing import remains limited to 50 rows per request; existing campaign, audience and reporting limits remain until separately redesigned. This is a proposal for independent design review, not an implemented or hosted-tested guarantee. The current shortlist's `limit=1001` / `>=1000` guard assumes a particular PostgREST maximum; a lower configured cap could silently truncate evidence, and remains an open issue even before pagination.

**Cohort and page contract.** Introduce a short-lived, server-created review session bound to exact tenant, authenticated staff actor, evidence mode and rules version. On creation the database selects IDs after applying the synthetic/business email-mode predicate, in deterministic UUID order, in one statement. Store the immutable ordered ID list and creation time, not source excerpts or credentials; cap the cohort explicitly (for example 5,000 IDs) and reject session creation if the cap would be exceeded, never silently truncate. Apply an expiry (for example 15 minutes), per-actor/tenant session and storage limits, and a cleanup path. IDs in the frozen list define the cohort at creation: newly inserted leads appear only in a new session, including IDs below an already viewed cursor. Pages use a validated session identifier and integer offset, not client-supplied IDs; reject wrong tenant, actor, mode, expired session, malformed offset or revoked staff access. Return the fixed cohort size, offset, page size, next/previous offsets, session expiry and explicit `cohortSnapshotAt`; never call page-local sorting a tenant-wide ranking. Deleted, moved, or mode-changed IDs become visible unavailable entries rather than being replaced by other contacts. Page navigation failures must retain the last successfully displayed page and permit retry, previous and restart. Mode or tenant changes discard the session and pending responses. Session reads are review-only and confer no rights, approval or execution authority.

**Atomic evidence completeness.** Add a service-role-only, security-invoker RPC with fixed empty search path and explicit EXECUTE revocations for public, anon and authenticated. Validate current staff eligibility and session ownership in the database, and fetch the requested ID slice plus the current tenant/lead, current brief, all same-tenant/same-lead observations in the chosen mode, current tenant/global suppressions and Response review owners in *one SQL statement* with a single PostgreSQL statement snapshot. Use bounded lateral aggregate/count subqueries per lead, not separate PostgREST table reads: independently count the complete qualifying set and assemble the complete array only when it is below an explicit per-lead evidence/byte cap. At or above that cap return an `evidence_overflow` entry with no evidence-derived assessment, products or actionable selector; other leads and subsequent pages remain accessible. Fail the entire page on a malformed RPC envelope, unexpected IDs, incomplete counts, oversized response or errors; no partial result may be assessed. Global and tenant suppression and owner lists also need bounded completeness checks, with a conservative hold or page error on overflow. Return one scalar JSON object containing the page and completeness metadata, rather than a PostgREST set of rows: a row limit cannot silently truncate its internal arrays. Validate byte and execution bounds before serialization and fail closed on any uncertainty. Consider statement timeouts and concurrency quotas so counts cannot exhaust the service.

The Worker validates the envelope, binds all returned IDs to that session/page, verifies counts and mode, and computes existing `assessProspect` / `reviewProducts` only for entries explicitly marked complete. Preserve the actual statement timestamp and brief version in each page. This provides complete input **at that statement's snapshot**, not a transaction spanning pages: a lead's evidence, suppression, reviewer status or brief may change before or after another page is loaded. Each page is a current read of its frozen membership; disclose this and provide refresh/restart. Prevent stale action authorization by continuing to re-read and validate relevant sources, current rights, reviews, suppression, tenant status and version under the existing database execution locks at each mutation/claim; a shortlist assessment or session token must never authorize an action. Do not rely on Worker rereads to create atomicity. Explicitly decide and implement what happens when the brief changes across pages: reject subsequent page requests with a restart instruction, or clearly display separate brief versions and prohibit a combined review; the safer default is restart.

**Migration and rollout.** Add private session metadata/ID storage and the bounded creation/read/cleanup RPCs in an additive migration; deny direct table access to client roles, and grant only narrowly required service access. Validate actual authorization, limits and query plans under production-like indexes and row counts. Define deterministic cleanup, expiry, rollback and deployment ordering. Keep old shortlist disabled or fail closed when the new RPC is absent or its acknowledgement cannot be validated; never silently fall back to independent PostgREST reads. Do not deploy a mixed Worker/schema pair. Review whether a single statement's snapshot covers every owner, stop, suppression and review dependency used by the existing rules; move any missing dependency into that statement or explicitly block the affected product. Retain existing no-live-send safeguards and do not apply migrations to production as part of local implementation.

**Consumers.** The prospect UI must expose first/previous/next/retry/restart, frozen cohort size and expiry, page-local ranking/counts and overflow rows; lead, evidence, inbox, Revive and product selectors may include only complete entries on the displayed page. The download must contain session ID, cohort and page scope, statement time and incompleteness notices; it is not a whole-cohort export. Response conversation choices and Events/Signal/Revive product history derive only from complete entries; Signal board must show page scope and explicitly distinguish no Signal history from blocked/overflow contacts. On page navigation/loading/error, invalidate selected conversation, Signal proposal, inbox/revive review and import preview, reject out-of-order responses and clear private prior-page content. The `rp:prospect-review-state` Signal listener must drop stale proposals, and the campaigns listener must invalidate a bound draft when its evidence review changes. Import preview must state that duplicate notices reflect only the page; the existing import RPC remains authoritative across the entire tenant and must not overwrite established identity. Separate campaign audience and outcome-report endpoints must not consume the page as an entire cohort or silently change their own limits; no bulk destructive operation may derive its target set from a page.

**Acceptance and remaining proof.** Test mixed modes before paging; more than 100 contacts across page boundaries; stable membership with inserts below and above a cursor, deletions and mode changes; tenant/actor/session isolation, expiry, revoked staff and malformed offset; concurrent evidence insertion/deletion, brief and suppression changes against independently connected PostgreSQL transactions; exact evidence and suppression cap boundaries with one overflowing contact, a complete neighboring contact and reachable later pages; small configured PostgREST row caps (including one) and an oversized scalar response; empty, malformed, reordered, duplicate and foreign RPC envelopes; failure/retry in both navigation directions; stale responses after tenant/mode/page changes; all listed consumers, selector exclusion, page labels and export provenance; existing SQL mutation/claim guards and no delivery. Review SQL statement-snapshot semantics and race tests independently, rehearse the migration and permissions on an isolated hosted environment and verify actual gateway scalar behavior and payload limits. Local PGlite or mocked adapters alone are not hosted proof. A frozen membership is not a frozen fact set or a whole-cohort ranking; delivery, import scalability beyond the stated bounds and operational acceptance remain open.

Newsletter links previously sent to `/api/newsletter/confirm?token=...` now display a no-store confirmation page; opening the link does not update state. An explicit form POST confirms only on an exact successful database receipt. The page has no external assets and sets a no-referrer policy; existing links still carry their token in the URL and may already be present in mail or access logs. This prevents ordinary link-preview GET requests from confirming subscriptions, but cannot distinguish a person from a scanner that submits forms. Provider delivery and hosted browser/proxy behavior remain unverified.

**Fresh design-review decisions (27 October).** These narrow the proposal above and must be incorporated before implementation:

- **Bounded completeness and payloads:** Use a deterministic `LIMIT cap + 1` probe in the same statement snapshot for each potentially unbounded lead, observation, suppression and owner set. The extra row means overflow; do not issue an unrestricted `count(*)` or aggregate an unbounded set before deciding. Aggregate only accepted rows. Establish explicit per-record, per-lead, per-page and scalar-JSON byte ceilings, including UTF-8 encoded size and metadata; reject oversized data before returning it. Validate reported item counts, complete flags, IDs and byte/shape limits at the Worker. Database and gateway timeout, malformed scalar or uncertain acknowledgement fail closed. Verify indexes and worst-case explain plans as well as limits under hosted configuration.
- **Brief and identity:** Freeze the current brief identity and version when the cohort session is created. Every page must check that exact version inside its evidence statement and return a restart-required conflict if it changes, including missing or replaced brief. Define evidence mode using the same canonical, validated lowercase email semantics used by import and assessment; filter by that canonical value *before* the cap-plus-one cohort probe and ordering. A malformed, null or changed email and a contact whose mode changes after cohort creation must be an unavailable entry, never silently reassigned or assessed in the wrong mode. Test mixed case, suffix boundaries, null and malformed records, and mode changes.
- **Session lifecycle and authority:** Generate unguessable opaque session IDs server-side; bind each to the exact tenant, staff actor, mode, frozen brief and expiry. Recheck actor's current staff eligibility and tenant/session binding on every operation, including cleanup where appropriate. Enforce quotas and expiry atomically in the database under overlapping creation requests, cap stored ID count and page size, and rate-limit creation. Store only minimum membership and metadata; define retention, periodic cleanup, ownership, audit visibility, and deterministic cleanup of expired sessions without exposing identifiers to other actors. Do not rely on token secrecy as authorization, and do not log contact lists or source excerpts.
- **Overflow recovery:** Display which contact is blocked and why, preserve navigation to its neighbors and later pages, and exclude the blocked contact from assessment-derived actions. Give staff a supported, authorized route to inspect and narrow or archive evidence without deleting audit history, then start a fresh session and reassess. That recovery path itself needs a separate immutable-history, authorization and concurrency design; until it exists, say the contact requires operator review and do not imply that a button or safe cleanup workflow already exists. Overflows in suppression or other safety inputs must conservatively block the affected result or page, never allow eligibility.
- **Current boundary:** Until a cap-independent database completeness contract is deployed and verified, the current PostgREST `limit=1001` guard is not sufficient if the server maximum is lower. Treat shortlist assessments as unverified for decisions that require complete evidence, preserve downstream execution checks, and do not describe the current 100-contact ceiling as a security guarantee. The failed pagination prototype was withdrawn. A production rollout must either make the existing route fail closed when completeness cannot be proven or replace it atomically with the verified RPC; a configuration assumption is not a proof.
- **Race acceptance:** Use independent real PostgreSQL connections and synchronization barriers to test creation quotas, snapshot membership, cap-plus-one probes, brief replacement, observation insertion/deletion, suppression addition/removal, reviewer revocation, lead deletion, tenant reassignment, email/mode changes, expiry and cleanup overlapping page reads. Establish whether each concurrent transaction commits before or after the single page statement snapshot, and assert results correspond to that snapshot or safely conflict; never infer atomicity across pages. Test response loss/retry, session expiry during a read, concurrent page requests and out-of-order browser results. Run these against an isolated hosted setup with deliberately varied PostgREST caps and actual scalar JSON payload/timeout limits; local mocks and serialized PGlite are insufficient.

**Bounded snapshot implementation attempt withdrawn:** Fresh implementation review identified that measuring `octet_length(to_jsonb(row)::text)` can force an arbitrarily large TOAST value to be materialized before the check. A row-count cap and a post-aggregation byte limit do not bound that work. The prototype also lacked a verified database execution-time/index strategy, a validated statement timestamp carried through a single assessment instant, and sufficient malformed-envelope and delayed-response tests. It was removed rather than presented as a completeness guarantee. A future implementation must prove bounded acquisition before materializing wide values, establish an enforceable timeout and suitable indexes, carry and validate the database snapshot timestamp, and pass independent review and hosted concurrency/gateway tests. The existing PostgREST completeness limitation remains open.
