## Step 1b: public consultation booking authority (RP-012)

The old `/api/book` accepted possession of a lead UUID and allowed `new` leads to book. The next CLI-generated migration `20261022083018_consultation_booking_capability.sql` adds nullable hash/expiry/use fields to existing leads without changing legacy data. A qualified `/api/lead` submission that passed Turnstile returns a random 122-bit UUID capability; only its SHA-256 digest is stored. The existing public form carries the token to `/api/book`. The Worker rejects missing, wrong-lead, expired, used and ineligible tokens before Calendar calls; a conditional database update atomically consumes the token before a meeting/provider side effect. A repeat inquiry rotates the token. The token is never placed in a URL, log, email, or browser storage by this change.

Synthetic verification: the Worker flow mock rejects guessed UUIDs, another lead's token, replay, expiry and an ineligible lead, with no Google event on rejected requests. PGlite validates the new migration and shows exactly one successful claim from two attempts. A partial unique index also rejects a second active consultation for the same lead at a different slot; a repeat inquiry for an already booked lead returns a neutral existing-request message without rotating its token or downgrading status. The live-form VM check confirms the frontend posts the returned token to the booking API. A Calendar/slot failure after consumption requires repeating the inquiry; this is safe but the recovery UX needs later polish. Turnstile reduces automated abuse at intake, but provider-side rate limits and verified ownership of the contact address remain release risks. The feature does not make the unconfigured production form operational. Reversal requires a code rollback coordinated with dropping the three nullable columns/check and partial index; old source would ignore them, so a forward code rollback is possible without immediate schema reversal.

### Confirmed defects and implemented corrections

- The previous `validFacts` substring check accepted `owner` inside `homeowner` and could treat `not the owner / no dormant leads` as matching evidence. Phrase boundaries now reject fragment matches. Conservative negative/uncertain/third-party wording screening sends observations to review and preserves the source excerpt. This is an English screening heuristic plus staff attestation, **not** semantic truth verification; paraphrases, other languages and implicit negation still require operator judgement. It deliberately prefers review over guessing.
- Canonical target/alias mappings are stored in the versioned brief and edited in its existing form. Only reviewed mappings apply. Unknown targets, ambiguous duplicate aliases and aliases matching excluded industries are rejected. No uncontrolled fuzzy matching or enrichment is used.
- The 90–100 headline score is removed (`score:null` retained for API compatibility). Industry/market/role/need and freshness remain separately inspectable. Readiness/engagement are not inferred from fit. Calendar-invalid dates, missing timezones and future observations are rejected.

### Shared data and UI path

`20261023013112_product_review_workflows.sql` was created with the cached Supabase CLI and `DO_NOT_TRACK=1`. It extends **existing** `lead_observations` with `product_context` and a tenant-scoped brief-version reference; no parallel lead/campaign store. New staff-only `product-event` and `prospect-import` endpoints use the existing auth and Db client. The existing shortlist response includes product review/history; products can be reviewed without another product or a completed business brief, while fit remains unknown until a brief exists.

Staff can paste up to 50 tab-separated rows into the Clients panel, with stable source reference, permitted-use reference and observation date. Each row reports created/linked/duplicate/rejected. PostgreSQL locks the tenant, uses existing case-insensitive tenant/email identity and existing observation uniqueness, and never changes contact rights or silently overwrites existing lead details. Missing provenance/mode errors stay rejected outside the operational audience. Retry uses the same reference; a changed source payload conflicts. Uncertain persistence errors stop the batch and tell staff to retry with unchanged references. Existing bounded review limits remain 100 leads and fewer than 1000 observations. Larger scale needs pagination, not silent truncation.

Reviewed product events are replay-safe and retain staff identity, source excerpt/date, permitted-use reference and current brief version. A response event atomically cancels queued follow-ups and moves claimed work to review. An opt-out inserts the existing objection request, invoking existing tenant/global suppression and rights freeze. The stop trigger is attached to observation insertion, and the existing synthetic dispatch eligibility function also refuses leads with a response/enquiry history, so a fresh campaign action cannot simply bypass the hold. Resuming after a human resolution is not implemented and cannot happen automatically.

The UI contains product-specific forms and expandable histories in the existing Clients panel. Sources are escaped; qualification questions never execute source instructions. A JSON download is labelled internal operator review, not a marketing contact list, and retains `contactAllowed:false`. Outcome history is manually verified and timestamped; counts/coverage are descriptive, not a conversion uplift claim. Unexpected API failures log only a route template and status, never raw database messages/source payloads.
