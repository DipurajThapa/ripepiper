The existing `deals.lead_id` and `meetings.lead_id` FKs accepted any lead UUID while owner RLS checked only the relation's `tenant_id`. A service-role path could also create a misleading cross-tenant attribution. The CLI-generated local migration `20261022082304_tenant_identity_foundation.sql` introduces composite `(tenant_id, lead_id)` FKs to `(tenant_id, id)` on leads, preserving the relation's tenant when a linked lead is deleted. A client-prospect meeting now requires a tenant. It leaves legacy NULL-tenant public consultation intake intact. It intentionally fails rather than silently repairing pre-existing mismatches; the migration includes read-only preflight queries. For an approved rollout, obtain a backup and review preflight rows; test a restoration or forward repair plan first. Reversal in development: drop both new FKs and the meeting check, restore the original single-column FKs, then drop `leads_tenant_id_id_key` after checking dependencies. This reversal is not a production instruction.

## Step 1b: public consultation booking authority (RP-012)

The old `/api/book` accepted possession of a lead UUID and allowed `new` leads to book. The next CLI-generated migration `20261022083018_consultation_booking_capability.sql` adds nullable hash/expiry/use fields to existing leads without changing legacy data. A qualified `/api/lead` submission that passed Turnstile returns a random 122-bit UUID capability; only its SHA-256 digest is stored. The existing public form carries the token to `/api/book`. The Worker rejects missing, wrong-lead, expired, used and ineligible tokens before Calendar calls; a conditional database update atomically consumes the token before a meeting/provider side effect. A repeat inquiry rotates the token. The token is never placed in a URL, log, email, or browser storage by this change.

Synthetic verification: the Worker flow mock rejects guessed UUIDs, another lead's token, replay, expiry and an ineligible lead, with no Google event on rejected requests. PGlite validates the new migration and shows exactly one successful claim from two attempts. A partial unique index also rejects a second active consultation for the same lead at a different slot; a repeat inquiry for an already booked lead returns a neutral existing-request message without rotating its token or downgrading status. The live-form VM check confirms the frontend posts the returned token to the booking API. A Calendar/slot failure after consumption requires repeating the inquiry; this is safe but the recovery UX needs later polish. Turnstile reduces automated abuse at intake, but provider-side rate limits and verified ownership of the contact address remain release risks. The feature does not make the unconfigured production form operational. Reversal requires a code rollback coordinated with dropping the three nullable columns/check and partial index; old source would ignore them, so a forward code rollback is possible without immediate schema reversal.

Source identity `(tenant, source, external_ref)` is unique; the contact-rights source must belong to the same tenant **and** lead. A permitted decision requires an identified reviewer and notice reference. Browser roles have no access unless platform admin; the service role retains server-only privileges. No live contact decision is granted by this migration.

## Step 2a: durable, synthetic-only action gate

The CLI-generated `20261022084845_campaign_execution_core.sql` migration adds tenant-bound campaign authority, global/tenant/campaign stop records and a uniquely keyed action ledger. A campaign is draft by default; an approved row requires nonempty client, owner and CTS references, expiry and a positive action limit. The only claim path is service-role-only and restricts destinations to `.invalid` email addresses. It atomically locks the action and campaign, checks active tenant, approval/asset versions, schedule/expiry/cap, current contact right, suppression and stop state, then records a two-minute lease. A separate test-sink completion rechecks the same eligibility rule and records `tested`, explicitly distinct from provider `delivered`. It **does not** contact anyone. An expired uncertain claim moves to review and pauses its campaign; it cannot be retried blindly.

PGlite exercises missing approval refs, replay, test-sink completion without a second effect, terminal review after lease, pause on uncertainty, global stop, stale approval version, objection between claim and completion, cross-tenant FK denial and viewer read denial. The durable state survives a simulated new claim call; an actual Worker restart and provider behavior are not yet verified. `POST /api/admin/actions/:id/test` uses the existing staff authentication and service-role RPC, requires `SYNTHETIC_SINK_ENABLED=true` (absent by default), and returns `tested` only after the database functions pass. Worker tests verify the disabled/default and unauthorized paths plus a mocked two-RPC success with zero email/Calendar calls. This is **mocked API + real PGlite SQL**, not a tested PostgREST/provider boundary. A real channel adapter and scheduled runner are **not implemented**, so M04-C/D/E remain partial and no campaign can deliver through this migration. The existing public/transactional email code is separate from this new prospecting ledger and still needs a scoped outbound safety review. Do not enable real schedules or infer campaign approval from reference strings alone.
